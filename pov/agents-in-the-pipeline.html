01The numbers

The numbers, and what they don't say

I compared the same three months every year, so the seasons line up. Over three years, the number of tickets we closed in that window grew about two and a half times.

It wasn't a straight line. Bugs got faster first, dropping to about a week and a half in year two and staying there. Everything else got slower in years two and three as the product grew. Year four is when it all moved together: the most tickets, the fastest median and the shortest slow tail. Today about half of all tickets close within ten days, and more than four in ten close within a week, up from about a third.

Ticket counts are only a proxy, so I lean on time to close. The method is the same every year: created-to-resolved time, epics excluded, and bulk backlog cleanups removed by the same rule.

02Context first

Write the context before the agent

Before Claude writes a line of code in a repo, it reads that repo's CLAUDE.md: a short guide to how the codebase is built and the rules we follow.

  • Architecture and a module map
  • Build, test and deploy commands
  • Conventions and naming rules
  • Known pitfalls and how to avoid them
  • Guardrails, like a Jira ticket ID on every branch, commit and PR

We're rolling one out to every repo, alongside shared hooks and skills. The payoff goes beyond code that matches our style. A product manager or support lead can ask how a feature actually works and get an answer grounded in the actual code, not a guess.

Guardrails live in tooling, not in a wiki. Hooks block work that has no Jira ticket, and Semgrep scans every pull request.

03The loop

Anyone can do any step but one

Every step of a ticket's life can be done by a person, by Claude, or both. Merging is the exception.

  1. TicketWritten and refined by a person or ClaudePerson · Claude
  2. ImplementCode and tests from the ticket and the repo's contextPerson · Claude
  3. Pull requestOpened with the Jira ticket IDPerson · Claude
  4. ReviewClaude in CI, and an engineer every timePerson · Claude
  5. MergeOnly an engineer can mergePerson
  6. QATested and verified by a person before releasePerson · Claude

Nothing merges on its own. Automation opens pull requests; people decide what ships.

04In production

The Playwright agent, running for real

Our clearest example is a QA agent. Every two hours it picks up Jira tickets that are done, writes a Playwright test and a matching test case for each, and opens a pull request. A QA engineer reviews every test before it merges.

On mobile, a second agent plans Maestro tests for app tickets. Writing those tests is the next step. Claude also reviews pull requests automatically in CI, and a set of shared plugins packages common jobs as skills.

05The human part

Where the agent still needs a person

  • Merging. Always a person, with no exceptions for small changes.
  • Review. An engineer reviews every pull request, whether a person or Claude wrote it.
  • Release. QA can use Claude to write and run tests, but a person verifies before anything ships.
06Takeaways

If you're starting this on your team

  • Write the context file before you write the agent.
  • Put guardrails in hooks and CI, where they run every time.
  • Measure time to close over the same window each year, not just ticket counts.
  • Let agents open pull requests. Keep the merge button human.
